Real Estate Finance App — A-to-Z Feature & Logic Spec

Source: Shopno Bilash Properties admin panel (Next.js + Prisma). Purpose: give the Finance App everything the admin panel already does, so nothing is missed. Rules marked MUST are non-negotiable because wrong numbers = real money loss.

1. Big picture

The admin panel is a real-estate developer platform. Money flows in 3 directions, and the Finance App must cover all of them:

FlowWho pays whomExamples
Money IN (sales)Customers → CompanyBooking money, down payment, installments, handover payments
Money IN (funding)Owners / Shareholders / Landowners → CompanyCost-allocation contributions per construction goal, with fines on delay
Money OUTCompany → Contractors, Vendors, Staff, Govt.Material purchases, contractor payments, project expenses, office/staff costs

Hierarchy: Project → Building → Floor → Unit. Every finance record carries an optional projectId so reports can be scoped per project or company-wide.

3. Modules & features (complete list)

3.1 Projects, Buildings, Floors, Units

  • Project: name, location, status, dates; sub-pages: Units, Parking, Construction, Documents, Expenses, Materials, Owners, Payments, Reports, Settings.
  • Building → Floor → Unit (flat/shop). Unit: size, price, status (available / booked / sold / owner-allocated / landowner-share).
  • A unit belongs to exactly one of: Customer (sold/booked), Shareholder allocation, Landowner allocation — never two at once.
  • Parking spaces (types, price, ownership assignment) and standalone Property listings (public website).

3.2 CRM / Leads

  • Lead: name, phone, interested project/unit, source, assigned salesperson, status; activity log (calls, visits, notes).
  • Lead → Customer conversion; reminders and notifications for follow-ups.

3.3 Customers

  • Profile, NID/contact, linked units, documents, payment history, outstanding balance, portal login (phone-based).

3.4 Sales workflow

  1. Booking — reserve a unit with booking money (unit becomes “booked”).
  2. Sale / Contract — agreed price, discounts, payment plan; unit becomes “sold”.
  3. Installments — schedule of due dates and amounts per contract.
  4. Payments — each receipt: amount, date, method, reference, receipt; allocated against installments.
  5. Cancellation — cancelled bookings/sales are excluded from totals; unit returns to available.

    Sales dashboardCustomers, sales count, total sales value, leads/enquiries
    ReceivablesPer customer: contract value, paid, outstanding, overdue installments
    Collection reportPayments received by period / project / method

    3.5 Shareholders & Landowners

    • Shareholder → Shareholdings per project (percentage/units) → contributions and payouts.
    • Landowner → Agreements (e.g. developer–landowner ratio, e.g. 40:60) → Allocations of specific units, plus any cash/advance terms.

    3.6 Cost Allocation / Owner Contributions (“Construction Goals”)

    When construction needs funding, admin creates a Cost Allocation (Goal) with total amount, date, fine rule and installments, then the system splits it across owners (by share/unit). Each owner gets an Owner Contribution (payable amount, due date, paid amount) and optional per-installment obligations. Admin can add Adjustments (waiver / discount / correction, ± amount) — the original payable is never changed.

    3.7 Procurement & Stock

    • Vendors, Material categories, Materials (with low-stock threshold), Purchase orders & Purchases (receipt, qty, rate, total).
    • Stock ledger: every purchase = IN, every usage/transfer = OUT; current stock = sum of movements.

    3.8 Construction & Contractors

    • Phases (foundation, structure, finishing…) per project, Tasks per phase with progress %.
    • Contractors: contract value, scope, payment schedule, Contractor Payments (advance / running bill / final).
    • Construction progress % derived from tasks; phase actual cost derived from real transactions (see §4).

    3.10 Documents, Approvals, Alerts, Reminders, Notifications

    • Documents: attached to Company / Project / Unit / Customer / Shareholder / Landowner / Vendor / Transaction, with visibility rules (what portal users may see).
    • Approvals: workflow for sensitive records; Alerts: budget overrun, overdue payments, low stock; Reminders & Notifications: due dates, follow-ups.

    3.11 Portals (read-only views for outsiders)

    • Customer portal: own units, installment schedule, payments, documents, dues.
    • Shareholder portal: own holdings, contributions, outstanding, fines.
    • Landowner portal: own agreements and allocated units.

    3.12 Admin utilities

    • Dashboard, Analytics, Activity feed, Audit log, Users & Roles, Company settings, Backup/export, Help.

    4. Calculation rules (the “hisab-nikash”) — MUST follow exactly

    Golden rule: compute everything at read time from source transactions. Never store a total or status that can go stale. Always filter by status, and use adjusted (effective) values — never raw sums.
    #QuantityFormula
    1Counts toward actual costInclude a transaction only if status is verified, completed or has no status. Exclude draft, pending, submitted, cancelled, rejected.
    2Project / phase actual costΣ(Purchases) + Σ(Project Expenses) + Σ(Contractor Payments), each filtered by rule 1.
    3Budget varianceBudgeted − Actual(live). Warn at 80% used, critical at 100% (per-row threshold overrides allowed). A manually typed “actual” field must be labelled “Actual (Manual)” — never show it as the real actual.
    4Effective payable (owner)payableAmount + Σ(adjustments). Original never mutated.
    5Outstandingmax(0, effectivePayable − paidAmount)
    6Overdueoutstanding > 0 AND dueDate < today
    7FineIf overdue: flat fine = fineValue; percent fine = outstanding × fineValue ÷ 100; else 0.
    8Total dueoutstanding + fine
    9Contribution statusoutstanding ≤ 0 → paid; else overdue → overdue; else paid > 0 → partially-paid; else pending.
    10Installment obligation statusoutstanding ≤ 0 → paid; due date passed → overdue; some paid → partially-paid; due within 7 days → due; else upcoming.
    11Total Payable (aggregates)Σ effectivePayable (not raw payable), so Payable − Paid always equals Outstanding even with waivers.
    12Goal collection %Σ paid ÷ Σ effective payable × 100.
    13Goal statuscancelled → archived → draft (admin decisions win) → completed (100% AND admin marked complete) → fully-funded (100%) → partially-funded (>0%) → upcoming (start date in future) → active.
    14Sales totalsExclude cancelled / non-final bookings and sales (same status-filter idea as rule 1).
    15Customer receivableContract value (after discounts) − Σ valid payments; overdue = unpaid installments past due date.
    16Stock on handΣ IN − Σ OUT from the stock ledger; alert when below material threshold.
    17Cash flowΣ money-in (customer payments, owner contributions, other income) − Σ money-out (counted expenses, contractor payments, purchases) per period.

    Self-check: if the same real-world number appears on two screens and they differ, that is a bug — fix it, don’t ignore it.

    5. Typical end-to-end flows

    1. Sale: Lead → Customer → Booking (booking money) → Contract → Installment schedule → Payments → Receipt → Receivable reaches 0 → Handover document.
    2. Construction funding: Create Cost Allocation → generate owner contributions → owners pay → system computes outstanding/fine each day → reminders → adjustments if waived → goal fully-funded → completed.
    3. Spending: Budget set → Purchase order / Purchase or Expense or Contractor Payment (draft → submitted → verified) → counted in actual cost only when verified/completed → budget alert at 80% / 100%.
    4. Month end: Cash-flow report, category report, contractor-payment report, owner-contribution report, receivables list; export for accountant.

    7. What the Finance App should do first

    1. Implement §4 formulas as shared functions (one place), then build screens on top.
    2. Build in this order: Accounts → Expenses/Project costs → Customer payments & installments → Owner contributions → Reports → Alerts.
    3. Keep roles, audit log and status workflow from §2 and §4 rule 1.
